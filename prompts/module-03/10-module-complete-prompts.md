# Module 3 Notebook: Completion and Transition

Use these prompts to retain the Module 3 evaluation framework and prepare for Workflow Integration.

---

## 1. Ten-point completion recall

```text
Without notes, explain these Module 3 rules in one sentence each:

1. Accountability stays with the releasing human or organization.
2. Evaluate against requirements, source material, and professional standards.
3. Accuracy and completeness require separate checks.
4. Plausible language is not verification.
5. Permit unknowns and define the evidence boundary.
6. Require auditable claim-to-source support.
7. Set human-review thresholds in advance.
8. Adapt content without changing factual invariants.
9. Use code execution for material calculations and review the logic.
10. End with release, edit, verify, escalate, or reject.

Afterward, identify any rule you could not explain precisely and create one remediation exercise.
```

## 3. Full release review

```text
Review this AI-assisted output using the complete Module 3 workflow.

Provide:
- intended use and audience;
- requirements review;
- accuracy review;
- completeness review;
- hallucination and inconsistency scan;
- source-grounding status;
- calculation or tool verification;
- Diligence threshold assessment;
- audience and disclosure review;
- format and reproducibility review;
- required reviewer and approval; and
- final disposition: Release, Edit, Verify, Escalate, or Reject.

For every material issue, state the controlling reason and next action.
```

## 5. Completeness stress test

```text
The visible claims in this output may all be correct.

Perform a completeness review by comparing the output with:
- the original requirements;
- expected source coverage;
- decision-relevant conditions;
- risks and dependencies;
- exceptions and limitations;
- required actions and owners; and
- applicable professional standards.

List what is present, what is missing, and whether each omission changes the release decision.
```

## 6. Verification-by-design repair

```text
Rewrite this prompt so the output is easier to verify.

Add:
- the permitted evidence boundary;
- explicit `unknown`, `not covered`, and `conflicting` behavior;
- precise citation or provenance requirements;
- quote-first extraction where appropriate;
- calculation or tool-execution requirements;
- support-status labels;
- required human-review thresholds; and
- release blockers.

Explain how each addition reduces verification cost.
```

---

## 7. Human-review gate exercise

```text
Determine whether qualified human review is mandatory.

Assess:
- stakes;
- reversibility;
- audience;
- regulatory, contractual, policy, or professional exposure;
- data sensitivity;
- uncertainty;
- evidence quality; and
- whether an irreversible action is approaching.

If review is required, define:
- reviewer expertise;
- approval authority;
- evidence access;
- review scope;
- intervention rights; and
- approval record.
```

## 8. Audience invariant check

```text
Compare these audience-specific versions against the verified source content.

Confirm whether every version preserves:
- facts and figures;
- units and dates;
- uncertainty;
- material risks;
- dependencies;
- required caveats;
- commitments; and
- approved organizational positions.

Flag any misleading omission, increased certainty, incompatible commitment, or disclosure problem.
```

## 9. Computation trust-chain review

```text
Review this code-executed result.

Check:
- authoritative input version;
- schema and field meaning;
- business rules;
- filters and date boundaries;
- units and currencies;
- duplicate and missing-value handling;
- code logic;
- row counts;
- reconciliation to control totals;
- chart and narrative consistency;
- reproducibility evidence; and
- required human approval.

Do not treat successful execution as proof of correctness.
```

## 10. Triage drill

```text
For each original scenario, choose:
- Ready to use;
- Needs revision; or
- Needs human override.

Then write:

[VERDICT] because [CONTROLLING REASON]; next, [REQUIRED ACTION].

Ensure the verdict considers both output condition and intended-use risk.
```

## 11. Module 3 to Module 4 bridge

```text
Take a verified AI-assisted task and map it into a workflow.

For each stage, identify whether responsibility belongs to:
- the language model;
- deterministic code;
- a tool or external system;
- persistent storage;
- a human reviewer; or
- an accountable approver.

Then identify:
- side effects;
- approval gates;
- failure modes;
- retries;
- state that must persist outside the prompt;
- observability; and
- rollback or correction behavior.

This is a transition exercise, not a claim that the Module 4 course outline is already complete.
```
